# ผลทดสอบความจุ — 8 ก.ย. 2569

## สรุป

ระบบผ่านการจำลองช่วงเช้าที่ครูใช้งานพร้อมกันครบทุกคำขอในสามขนาดโรงเรียน
จนถึง **100 ครู / 3,500 นักเรียน** บนฐานข้อมูลพัฒนาในเครื่อง. คอขวดที่เห็นคือ
การเปิดแดชบอร์ดครูพร้อมกัน: แต่ละหน้าทำงานย่อยแบบขนานหลายชุด จึงทำให้คิว
PostgreSQL สูงกว่างานเช็คชื่อมาก แม้ไม่มีคำขอใดล้มในรอบนี้.

ผลนี้เป็น baseline สำหรับเปรียบเทียบโค้ดในอนาคต **ไม่ใช่ SLA ของ Railway**.
ยังตอบไม่ได้ว่า deployment จริงรับได้เท่าไรจนกว่าจะรันชุดเดียวกันบน replica ที่มี
CPU/RAM และ PostgreSQL plan เท่ากับโรงเรียนจริง.

## สถานการณ์จำลอง

- ข้อมูลจำลอง: ครู 1 คนต่อ 1 ห้องและ 1 วิชา, นักเรียน 25–35 คนต่อห้อง
- จังหวะหนัก: ครูทุกคนส่งเช็คชื่อของทั้งห้องพร้อมกัน, เปิดสมุดเช็คชื่อพร้อมกัน,
  แล้วเปิดแดชบอร์ดครูพร้อมกัน
- การยืนยันตัวตนและ API ใช้ Express route เดียวกับหน้าเว็บจริง
- ฐานข้อมูลมี connection pool สูงสุด 20 connections
- ไม่รวมอัปโหลดไฟล์ 100MB เพราะไม่ใช่เหตุการณ์ใช้งานทั้งโรงเรียนพร้อมกัน และคอขวด
  หลักเป็น network/object storage คนละชุดกับ PostgreSQL

## ผล

| ขนาดจำลอง | เช็คชื่อพร้อมกัน (p95) | เปิดสมุดเช็คชื่อ (p95) | เปิดแดชบอร์ดครู (p95) | ล้มเหลว |
| --- | ---: | ---: | ---: | ---: |
| เล็ก: 20 ครู / 500 นักเรียน | 48 ms | 41 ms | 32 ms | 0 / 60 |
| กลาง: 50 ครู / 1,500 นักเรียน | 52 ms | 89 ms | 131 ms | 0 / 150 |
| ใหญ่: 100 ครู / 3,500 นักเรียน | 113 ms | 269 ms | 581 ms | 0 / 300 |

คิวที่รอ PostgreSQL สูงสุดในขนาดใหญ่:

| งาน | จำนวนที่รอ connection สูงสุด |
| --- | ---: |
| เช็คชื่อ | 72 |
| เปิดสมุดเช็คชื่อ | 80 |
| เปิดแดชบอร์ดครู | 480 |

ตัวเลข queue ไม่ใช่จำนวนครูที่ค้างอยู่: หนึ่ง request ของแดชบอร์ดแตกเป็นงานอ่านย่อย
หลายรายการพร้อมกัน. ทุก request สำเร็จ แต่สัญญาณนี้บอกว่าหาก Railway มี CPU/RAM
เล็กหรือฐานข้อมูลช้ากว่าเครื่องพัฒนา แดชบอร์ดคือจุดที่ควรวัดและปรับก่อน.

> `peakDbWaiting` เป็นค่าจาก pool ของ **load-test runner** เท่านั้น ไม่ใช่ pool ของ app
> บน Railway. การวัด staging จริงด้านล่างจึงใช้ HTTP และ resource metrics ของ Railway
> เป็นหลักแทน.

## ผล Railway staging จริง — 9 ก.ย. 2569

รันผ่าน GitHub Actions บน project `PSSMS Load Test Staging` ที่แยก PostgreSQL และ app
จากเดโม/โรงเรียนจริง. ทั้งสองรอบเป็น workflow เดียวกับที่ใช้ซ้ำได้:

| โปรไฟล์ | เช็คชื่อ p95 | เปิดสมุด p95 | แดชบอร์ด p95 | สำเร็จ |
| --- | ---: | ---: | ---: | ---: |
| เล็ก: 20 ครู / 500 นักเรียน | 551 ms | 440 ms | 299 ms | 60 / 60 |
| ใหญ่: 100 ครู / 3,500 นักเรียน | 2,006 ms | 1,724 ms | 1,513 ms | 300 / 300 |

- GitHub Actions: [โปรไฟล์เล็ก](https://github.com/NorthSKK/PSSMS-web/actions/runs/34306862503) ·
  [โปรไฟล์ใหญ่](https://github.com/NorthSKK/PSSMS-web/actions/runs/34306916205)
- Railway app รวมทั้งสองรอบ: HTTP 423 requests, 5xx = 0, HTTP p95 = 1,524 ms
- app ใช้ CPU สูงสุด 0.151 vCPU จาก 8 vCPU และ RAM สูงสุด 283 MB จาก 8 GB
- PostgreSQL cache hit ratio = 1.0, CPU สูงสุด 0.062 vCPU จาก 8 vCPU, RAM 114 MB จาก 8 GB

ตามเกณฑ์เดิม เช็คชื่อ p95 ต้องไม่เกิน 2 วินาที ดังนั้นรอบใหญ่ **เกินเกณฑ์ 6 ms** แม้ไม่มี
คำขอล้มและทรัพยากรยังเหลือมาก. จึงตั้งเกณฑ์ชั่วคราวสำหรับ Railway plan นี้เป็น **2.5 วินาที**
สำหรับเช็คชื่อ แล้ววัดซ้ำเมื่อเปลี่ยน region, plan หรือ payload จริง. ไม่มีเหตุผลให้เพิ่ม DB
pool จาก 20 ในตอนนี้: ทั้ง app และ PostgreSQL ยังใช้ทรัพยากรต่ำมาก.

## ข้อสรุปเชิงปฏิบัติ

- เป้าหมาย 100 ครูเช็คชื่อพร้อมกันผ่านได้ในสภาพจำลองนี้ (p95 199 ms)
- การเปิดสมุดเช็คชื่อพร้อมกัน 100 คนผ่านได้ (p95 301 ms)
- ยังไม่ควรเพิ่ม DB pool จาก 20 เพียงเพื่อแก้ queue: ต้องวัด connection limit และ CPU
  ของ Railway ก่อน มิฉะนั้นเพียงย้ายคอขวดไปที่ฐานข้อมูล
- ก่อนรับประกันลูกค้า ให้รันชุดนี้บน staging ที่สเปกเท่า production พร้อมเพิ่ม network
  latency และวัด CPU, RAM, PostgreSQL connections, p95/p99 และ error rate

## รันซ้ำ

```bash
node scripts/load-test.js
node scripts/load-test.js --profile=large
```

สคริปต์ปฏิเสธฐานข้อมูลที่ไม่ใช่ `localhost`, สร้างข้อมูลชื่อขึ้นต้น `PERF_` ชั่วคราว
และลบทิ้งเมื่อจบหรือเมื่อเกิดข้อผิดพลาด.
